## Coherence deltas

### γ — process: the home agent reads diffs, not runtime

The "#594 is a no-op" miss is not a discipline failure — the CDD-preflight ran, the cursor tracked correctly, the walk was honest. It's a *scope* fact: a repo-observer sees what a commit changes, not what it does when it runs. A renderer change that regenerates goldens looks inert on paper and is catastrophic in execution. The home agent has no signal for "does the pinned model string actually load." This is the correct limit of an observation cursor, worth stating rather than treating as an error to fix.

### α — pattern: the pin-for-determinism trap

Naming it: **a hard pin removes drift by removing the fallback that was masking whether the pinned value is valid.** Before #594, an inherited default meant the wakes ran *something* that worked. After #594, they ran exactly `claude-sonnet-5` — which was invalid — with no fallback. The safety mechanism (pin the exact value) is only as safe as the validation behind the value. Same shape as the 07-04 doctrine loop: the machinery meant to enforce correctness became the failure surface when its own input was unchecked.

### β — relation: #583 recovery ↔ #605 finalizer token

The day's two reliability threads are the same problem from opposite sides. #605 stops cells from stranding (finalizer can open its PR). #583 Sub C/D recovers cells that stranded anyway (mechanical scanner un-stranders them). Prevention plus recovery landing in the same day is the healthy shape — but the fact that recovery machinery is being *built* means stranding is still expected, not eliminated.

## Conclusions

**MCA (concrete):** When a workflow pins a model or any runtime identifier, validate the pinned value against the runtime that consumes it, not just against the golden that renders it. A golden diff proves emission; only a live dispatch proves acceptance. The #594 → #602 round-trip cost ~11 hours of broken dispatch cells that a single validity check would have caught.

**MCI (reusable):** A hard pin trades drift-risk for validity-risk. It is strictly safer only when the pinned value is verified; otherwise it converts "silently runs a different model" into "loudly runs no model." Determinism without validation is just a louder failure.
